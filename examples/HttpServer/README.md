# HTTP server example

This example is a small asynchronous demo server for Extora. It supports
streaming object bodies and basic S3-style operations, including versioning
and multipart uploads. It is meant for local testing and does not implement a
complete S3 server.

## Build and Run

Boost 1.92.0 is fetched automatically when the example is enabled. The server
uses `extora::asio` to run storage operations without blocking its network
event loop.

```sh
cmake -S . -B build/http-server \
  -DEXTORA_BUILD_EXAMPLES=ON \
  -DEXTORA_BUILD_HTTP_SERVER_EXAMPLE=ON
cmake --build build/http-server --target extora_http_server_example
build/http-server/examples/HttpServer/extora-http-server-example
```

Optional arguments:

```text
extora-http-server-example \
  [address] [port] [storage-directory] [multipart-min-part-size]
```

The defaults are `127.0.0.1`, `8080`, `extora-http-server-store`, and `5242880`.
Open <http://127.0.0.1:8080/> for the endpoint documentation and curl examples.

## Postman Collection

A Postman collection is available at
[`Extora HTTP Example.postman_collection.json`](<postman/Extora HTTP Example.postman_collection.json>).

For the guided workflow, start the server with an empty storage directory:

```sh
build/http-server/examples/HttpServer/extora-http-server-example \
  127.0.0.1 8080 /tmp/extora-postman-store
```

Import the collection and click its numbered folders and requests from top to
bottom. Request bodies are embedded or generated by the collection, and
response scripts propagate version and upload identifiers automatically. The
first multipart part is generated at the default minimum size of 5 MiB, so no
multipart size override is required. The incorrect-checksum request is the only
request expected to fail; it should return `checksum_mismatch`. Use a new empty
storage directory when repeating the complete workflow.
